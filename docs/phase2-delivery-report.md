- Reviewer: deposit cards rounded to whole units and added payables to receivables -> paise shown when fractional,
  cards split into Deposits to pay / Paid / Pending to pay / To receive.
- Reviewer: SD-2 could 500 on a concurrent supplier delete -> transaction with the supplier share-locked; correlated
  subqueries nested so drizzle keeps table qualifiers; deterministic ordering tie-breaks.
- Reviewer: RPT-O2 showed "₹0.00" per piece beside a "–" landed cost -> both null at zero cost; container state in the
  report derived from its clearing/trip; zero excess/short printed with the unit; header buttons fit a 375 px phone.
- USR-5 (user delete) did not count the new `created_by` columns -> added to `REFERENCES`.
- e2e: `units-po.spec.ts` assumed the new order sat on page 1 of /orders -> searches first; the new deposits spec

## D. Database

Migration **`drizzle/0008_deposits.sql`** (generated by drizzle-kit, additive only, idempotent defaults):

- `payments` + `reference text not null default ''`, `notes text not null default ''`.
- `supplier_deposits` (id, supplier_id -> suppliers, direction `give|receive`, amount > 0, currency, opened_on,
  reference, notes, timestamps, created_by) + index on supplier_id.
- `supplier_deposit_transactions` (id, deposit_id -> supplier_deposits **on delete cascade**, paid_on, amount > 0, mode,
  reference, notes, timestamps, created_by) + index on deposit_id.

No existing table, row, relation or index is changed. Backward compatible both ways: the old backend ignores the new
columns; the new backend reads them, so **0007 and 0008 must be applied to production before this backend is deployed**
(the API has no migrate-on-boot). No migration was run anywhere but the local test databases. Nothing stored for
closure or deposit status: both are derived live.

## F. Known limitations, assumptions, risks

1. **Closure rule** (decision): closed = stage 6 and every container carrying the order has a stocked warehouse receipt,
   which is the landed-cost "waiting for warehouse" rule already in the code. Goods received in China but never loaded
   before the first container clears cannot be loaded later (existing CON-2 behaviour); such an order still closes.
2. **Reopening** exists only through WH-4 (Management deletes a stocked receipt; server log line). No new reopen flow.
3. **Pending deposits**: no "deposit required" per order exists, so pending = `due` deposit records, which no screen
   creates today. Adding deposit terms to an order is a product decision.
4. **Paid figures**: the All orders tab's "Paid so far (INR)" and the Deposits & Payments page keep every payee (as
   before); the new tabs, the order report and Order reports use supplier-only figures (13.5). Both are labelled.
5. Excel `autoFilter` is written without Excel's own `_xlnm._FilterDatabase` defined name; XML validates in tests,
   desktop Excel was not opened here.
6. `/orders/pending` and `/orders/closed` are static routes, so a PO literally named "pending" or "closed" is unreachable by URL.
7. Lists still load every order/deposit and filter on the client (the existing pattern); fine at hundreds, revisit at thousands.
8. The Report tab's export buttons sit in the tab content, not the shared order header.
9. Pre-existing, not fixed here: `/calendar` month view overflows a 390 px phone when deliveries exist (`round3-regression` 390x844), reproduced on the pre-phase base. The browser suite on this machine also has known stalls (one 7-minute `page.reload`, one aborted navigation in the full run; both passed when re-run).
